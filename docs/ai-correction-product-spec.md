# AI 修正 —— 产品方案

> 状态：设计稿（未实现）
> 日期：2026-07-28

## 1. 要解决的问题

现在的识别结果有三类错误，性质完全不同：

| 类型 | 例子 | 现有手段 | 现状 |
|---|---|---|---|
| **无歧义固定错** | 克劳德 → Claude | 替换规则 | 能治，但要手工维护 |
| **有歧义错** | cloud ↔ claude（两个词用户都会说） | 替换规则 | **治不了，且强行治会误伤** |
| **低频长尾错** | 偶发同音字、专名 | 替换规则 | 治不了，规则永远补不全 |
| **断句/排版** | 全部挤成一整段 | 无 | 治不了 |

用户自述的痛点「规则覆盖不全，犯的错也时常有变化」，本质是**用无状态的字符串替换去对付有状态的语言问题**。

`TextReplacer.apply()` 是无条件 `replacingOccurrences`。一旦用户日常同时使用 `cloud` 和 `claude` 两个词，规则 `cloud → claude` 就会把真正的 cloud 也改掉。**这是现有机制固有的缺陷，不是本方案引入的**，但它决定了下面所有设计。

**结论不是"用大模型取代规则"**，而是建立三层结构，各治各的：

```
第 0 层  火山热词表        识别前干预，从源头减少错误，零延迟
第 1 层  本地替换规则       零延迟零成本，只治「无歧义」的固定错
第 2 层  大模型修正         有延迟有成本，治有歧义 / 长尾 / 排版
         ↓
         纠错沉淀：第 2 层反复改同一个词，且改动无歧义 → 提示下沉到第 0/1 层
```

第 2 层不是终点，是**发现器**。它发现的稳定模式要往下沉，否则每次都要花 2 秒和一次 API 调用去修同一个词。这是整个方案的核心闭环。

**但下沉必须过歧义关。** 有歧义的改动（cloud/claude）**永远不能下沉成规则**，只能留在模型层靠语境判断——那正是模型不可替代的地方。详见 §7.2。

## 2. 两档模式与快捷键

### 2.1 心智模型

不叫"要不要开修正"，叫**两档质量**，用不同快捷键选：

| 档位 | 快捷键 | 行为 | 延迟 |
|---|---|---|---|
| **精修模式**（默认档） | 右 Option 单击 | ASR → 替换规则 → 大模型 → 粘贴 | +1~3 秒 |
| **快速模式** | 右 Option + ←  | ASR → 替换规则 → 粘贴 | 同现在 |

按用户指定：最省力的单键给精修（日常主力），组合键给快速（要快时用）。

**技术可行性说明**：现有触发逻辑是「纯修饰键单独按下并释放时触发」，且按下期间检测到其他键就拦截。所以「按住右 Option 再点左箭头」天然不会触发单键流程，可以干净地映射到第二条流程，不会互相误触。

### 2.2 补一个入口：快速模式说完后再补修正

单靠开口前选快捷键有个问题——**你往往说完了才知道这段值不值得润色**。

**面板底部提供一个「修正」按钮**（快速模式下可见），配 `⌘Return` 快捷键。按钮是主入口（可发现），快捷键是加速方式。

**但这里有个流程矛盾必须先解决**：快速模式是立即粘贴的，等你看到面板并点了修正按钮，文本早就贴出去了。如果修正结果自动替换已粘贴内容，就回到了 §3.1 明确否决的"先粘贴后替换"。

所以按钮行为定义为：

1. 快速模式粘贴后，**面板不立即关闭**，停留至失焦或 `Esc`
2. 点「修正」→ 跑一次修正 → 结果显示在面板，**并写入剪贴板**
3. 面板提示「已复制修正版，⌘V 粘贴」；也可用现有的「粘贴最后识别结果」快捷键重贴
4. **不自动替换已经贴出去的文本**

代价是用户要多按一次 `⌘V`。这是诚实的代价——比一个会偶尔毁掉用户文档的自动替换好。

这样两档模式从"事前选择"变成"事前默认 + 事后可补"，覆盖真实使用节奏。

### 2.3 面板上的「退回修正前」按钮

修正结果不满意时，面板提供一个按钮在**修正版 / 原文**之间一键切换。切换后的内容就是即将粘贴（或用「粘贴最后识别结果」重新粘贴）的内容。

这与 §2.2 的「修正」按钮解决的是两个相反方向的问题，两者都保留：

| 入口 | 出现在 | 解决的问题 |
|---|---|---|
| 「退回修正前」 | 精修模式 | 模型改错了 / 改过头了 → 我要原文 |
| 「修正」（`⌘Return`） | 快速模式 | 说完才发现这段值得润色 → 补一次修正 |

### 2.4 备选（不推荐，仅记录）

右 Option 双击 = 快速模式（复用现有 singleTap/doubleTap 机制，无需新增组合键类型）。比左箭头更好按，但双击有 ~200ms 判定延迟，反而拖慢"快速"档，与其定位矛盾。所以采用用户原方案。

## 3. 延迟策略 —— 本方案最关键的取舍

语音输入的核心价值是即时。修正必然加延迟，怎么处理决定这个功能是好用还是折磨。

### 3.1 三种可能，选一种

| 方案 | 描述 | 评价 |
|---|---|---|
| A. 阻塞等待 | 面板显示"润色中"，修正完成再粘贴 | ✅ **采用** |
| B. 乐观粘贴 | 立即粘贴原文，修正回来后在原位替换 | ❌ 否决 |
| C. 只写历史 | 立即粘贴原文，修正结果只进历史不改正文 | 作为快速模式的可选增强 |

**为什么否决 B**：在别人的 app 里替换已粘贴文本，需要模拟选中 + 删除 + 重粘，依赖焦点没变、文本没被改动、目标控件支持选择——任何一条不满足就会破坏用户的文档。这是典型的"用奇怪手段解决问题"，且失败后果不可逆。不做。

**A 的关键护栏 —— 超时降级**：修正超过 **6 秒**自动放弃，直接粘贴规则处理后的原文，面板角标提示「修正超时，已粘贴原文」。语音输入绝不能卡死等模型。任何失败（无 key / 网络断 / 返回异常）都走同一条降级路径。

### 3.2 各引擎的延迟预期

| 引擎 | 单次修正预期 | 说明 |
|---|---|---|
| GLM `glm-5.2`（关 thinking） | 1~3 秒 | ai-info 实测重任务 4~17s，本场景输入极短，取低端 |
| Claude API Haiku | ~1 秒 | 最快 |
| Claude API Sonnet | 1~3 秒 | |
| Claude 订阅（无头 CLI） | **5~15 秒+** | 每次要冷启动进程；内存压力下更慢 |

无头方式的延迟对语音输入基本不可接受。见 §5.3。

## 4. 修正做什么、不做什么

### 4.1 排版交给模型，不做成设置

**分段、标点、断句全部由模型在 prompt 里按语义决定，不给用户开关。** 理由：这些是文本的语义属性，模型看得见——短句就该保持单行，长指令就该分段。做成"不动/轻/重"三档设置，或者用「< 40 字不分段」这种字符阈值代理，都是把模型比我们判断得更准的事情硬编码成规则。

prompt 里给方向即可：*"按语义分段并补齐标点；短句保持单行，不要为了分段而分段。"*

### 4.2 唯一保留的内容开关：口语赘词

有一件事模型**从文本里推不出来**：你要不要保留"呃 / 那个 / 就是说 / 然后呢"。同一段文本，有人要逐字保真（会议记录、引述），有人要清理干净（写指令、写文档）。这是使用者偏好，不是语义属性。

| 选项 | 行为 |
|---|---|
| 保留原话 | 只纠错、只排版，不动措辞 |
| **清理赘词**（默认） | 额外去掉口头禅、重复词、明显的自我打断 |

**这个开关切换的是两套 prompt，本地不做任何赘词处理。**

绝不能在本地维护一份 `呃 / 那个 / 就是说` 的词表去删——「**那个**文件在哪」里的"那个"是指示代词，不是赘词。赘词和实词的区别只有语境能判断，本地词表必然误删。

纠错本身（同音字、专名、中英混排）不设开关——开了 AI 修正就一定纠错，那是这个功能存在的理由。

### 4.2.1 通则：本地只做确定性处理

上面几条其实是同一条原则的不同侧面，立为通则：

> **本地只做确定性的、无歧义的处理；任何需要语义判断的，一律交给模型。**

违反它的典型形式：

| 反例 | 为什么错 |
|---|---|
| 本地赘词词表 | 删不掉的语境差异（"那个文件"） |
| `< 40 字不分段` 字符阈值 | 用字数代理语义完整性 |
| 把映射式替换规则喂给模型（§6.1.1） | 用规则的机械性覆盖模型的语境判断力 |

三者都是"用规则去做模型该做的判断"。设计时凡是想加一条本地启发式，先问：这件事需要理解意思吗？需要就交给模型。

### 4.3 防"改过头"护栏

模型最大的风险是自作主张改写内容。产品层面加三道：

1. 提示词硬约束：只允许改字词与断句，禁止增删语义、禁止解释、禁止回答文中的问题
2. **长度护栏**：修正后字数相对原文变化超过 ±30% → 判定异常，丢弃修正结果，用原文
3. 面板 diff 高亮：修正版默认展示，变动处高亮，一键切回原文对照

第 3 条不只是安全网，更是**信任建立机制**——用户能亲眼看到 cloud→claude 被改对了，而不是把结果当黑盒吞下。

### 4.4 与现有 `removeTrailingPunctuation` 的冲突

现在的规则层会去掉句尾标点。修正开启时这会和模型的排版结果打架。规则：**精修模式下跳过去尾标点，标点由模型决定；快速模式维持现状。**

## 5. 修正引擎的产品设定

### 5.1 核心设计：用「质量档」而不是模型名

用户问"API 调用是不是也要指定模型"——要，但**不该让用户填模型 ID 字符串**。模型名会过期（`glm-4.5-flash` 已下线自动路由）、含义不透明、跨服务不可比。

产品上做成两层：

**第一层：选服务**（三选一）

**第二层：选质量档**（每个服务把档位映射到自己的模型）

| 质量档 | GLM | Claude API | Claude 订阅（无头） |
|---|---|---|---|
| 快 | `glm-5.2` | Haiku | —（无头本身就慢，不提供） |
| **均衡**（默认） | **`glm-5.2`** | Sonnet | **Sonnet** |
| 高 | `glm-5.2` | Opus | Opus |

**GLM 目前只有一个可用模型**（2026-07-31 实测：`glm-4.7-flashx` 返回 429 code 1113 余额不足，
免费 flash 系有共享池拥塞），所以三档全部映射 `glm-5.2`。**服务商只有一个可用模型时，
设置界面隐藏档位选择**——摆三个一模一样的档位是假选择。档位枚举保留给 Claude API，
那里 Haiku / Sonnet / Opus 才是真实差异。

**第三层（折叠在「高级」里）**：自定义模型名输入框。给愿意折腾的人留口子，但不挡在主路径上。

这样用户面对的是"要快还是要准"，而不用去分辨具体模型 ID 的差别。模型迭代时我们改映射表，用户无感。

### 5.2 三种引擎的定位

| | GLM API | Claude API | Claude 订阅（无头） |
|---|---|---|---|
| 延迟 | 1~3s | 1~3s | 5~15s+ |
| 成本 | 按量，极低（本场景每次几厘） | 按量 | 已付订阅，边际零 |
| 配置成本 | 填一个 key | 填一个 key | 需本机装 Claude Code 并已登录 |
| 定位 | **默认推荐** | 质量优先 | 已有订阅、不在意延迟 |
| 分发版 | ✅ | ✅ | ✅（需知情告知，见 §5.3） |

**默认推荐 GLM**：本机已有 `GLM_API_KEY`（keychain，跨项目共享），ai-info 已跑通同一端点，成本实测极低，延迟可接受。

必须继承 ai-info 的两条硬经验：
- **必须关 thinking**（`extra_body: {"thinking": {"type": "disabled"}}`）。GLM 默认是 thinking 模型，不关会平白烧 100~195 reasoning token、耗时 50~80s，且 thinking 吃 max_tokens 预算会截断输出。
- **不要用免费 flash 档**。共享池拥塞（429 code 1305）会把请求拖到分钟级。语音输入完全承受不了。

### 5.3 无头 Claude 订阅：可行且正当，只是慢

**可行性：已验证。** Claude Code CLI 支持 `claude -p` 非交互模式，直接复用本机已登录的订阅凭证（macOS keychain 中的 `Claude Code-credentials`）。app 只需 spawn 子进程，**不需要自己接触 token**——避免了 app 代持凭证带来的安全和权限问题。这条路在本机 ai-info（早期）/ inv-assistant（至今）已长期运行。

**正当性：不是灰区。** 这是用户在自己机器上调用自己安装、自己登录的官方 CLI 的官方 headless 模式，app 只是 spawn 子进程，不代持凭证、不做代理、不转卖额度——与任何 shell out 到本地 CLI 的工具没有区别。**选择权应当交给用户。**（真正的灰区是服务商订阅被第三方代理转售，本方案不涉及。）

**真实约束只有两条：**

1. **延迟 5~15 秒**。每次调用都要冷启动一个 Node 进程加载 CLI，内存压力下更慢。这是它当不了默认档的**唯一**原因。
2. **消耗订阅额度**，与用户自己写代码共用同一个池子，跑满会被限流。

**产品处理**：作为并列的第三个引擎选项正常提供，不隐藏。但因为上面两条，需要**知情告知**——选中该引擎时在设置里直接显示：

> 将使用本机 Claude Code 的登录态运行，**消耗你的 Claude 订阅额度**（与写代码共用）。延迟通常 5~15 秒，明显高于 API 方式。需已安装并登录 Claude Code。
>
> VoiceInput **不读取、不存储、也无法访问**你的 Claude 账号凭证——登录态完全由 Claude Code 自己管理，本应用只是启动它的命令行进程。我们也不会访问你的 Claude 对话历史或任何其他账号数据，只把当前这段识别文本交给它、取回修正结果。

第二段是**机制陈述而非承诺**，这一点很重要：app 从头到尾没有读取 keychain 里的 `Claude Code-credentials`，是 CLI 自己去读的。用户可以验证。泛泛说"我们不会滥用你的数据"没有说服力，说清楚"结构上不可能"才有。

不做默认档，不在首次引导里推荐——理由是延迟，不是合规。

**如果要救延迟，唯一办法是常驻进程**（长驻一个 CLI 会话反复喂输入，而不是每次冷启动）。但这引入进程生命周期管理、僵死恢复等复杂度。建议 v1 不做，先用 API 方式验证功能价值。

**如果确实要用它，唯一能救延迟的办法是常驻进程**（启动一个长驻 CLI 会话反复喂输入，而不是每次冷启动）。但这引入进程生命周期管理、僵死恢复等复杂度，性价比不高。建议 v1 不做，先用 API 方式验证功能价值。

## 6. 上下文设计

用户的核心诉求：`claude` 常被识别成 `cloud`，但如果模型知道你最近一直在说 claude，就该修对。

### 6.1 送什么进去

| 内容 | 为什么 | 优先级 |
|---|---|---|
| **最近 N 条识别记录** | 建立话题连续性，解决 cloud→claude | 必须 |
| **专名词典（只有词，没有映射）** | 告诉模型这些词在这个人的语境里存在 | 必须 |
| **目标 app 名称** | 往终端说话 vs 往微信说话，术语域和格式期望完全不同 | 推荐 |

### 6.1.1 关键：送词，不送映射

**绝不能把替换规则原样送进模型。**

规则 `cloud → claude` 是一条**强制指令**。喂给模型，模型就会照做——于是用户真正想说 cloud 的那次也被改掉了。这等于把规则层"无法做语境判断"的机械缺陷传染给了本来具备语境判断能力的模型，**自废武功**。

正确做法是只提取规则右侧的**目标词**，连同火山热词表，合成一份「专名词典」：

```
✅ 送这个：
   这个用户常用的专有名词：Claude、Claude Code、Berth、KeyFlow、火山引擎、Karabiner…

❌ 不要送这个：
   把 cloud 改成 claude
```

模型拿到词典只知道"这些词存在于这个人的世界里"，然后**靠上下文自己判断**这一句说的到底是 claude 还是 cloud。这正是模型相对规则的核心优势。

### 6.1.2 推论：专名词典应取代替换规则成为主入口

「只列词、不列映射」比「替换规则」更符合直觉，也没有机械替换的副作用。而火山热词表**本来就是这个形态**（只有词，没有映射）。所以一份数据两处用：

```
我的专名词典 ──┬──→ 火山热词表（识别前干预，从源头修）
               └──→ 模型上下文（识别后按语境修）
```

**替换规则降级为「高级」功能**，保留给确实需要无条件强制替换的场景（例如固定的格式转换）。UI 上「专名词典」在前，「替换规则」折叠在后并附风险提示：*"无条件替换，若该词在其他语境也合法会误伤。"*

### 6.2 用哪个版本的历史文本

用户明确提到"如果用户手动改过，当然要传改后的"。历史记录需要三个字段：

| 字段 | 含义 |
|---|---|
| `text` | ASR 原始输出 |
| `corrected` | 大模型修正后（新增） |
| `edited` | 用户在面板里手改后 |

**送入上下文的优先级：`edited` > `corrected` > `text`**。用户手改的是最强信号——那是他真正想要的写法。

### 6.3 窗口大小

默认 **最近 5 条 且 在 10 分钟内**。双重限制的理由：
- 只限条数：昨天的 5 条会污染今天的话题
- 只限时间：连续快速输入时可能塞进几十条，浪费 token 且稀释信号

上下文只传文本，不传时间戳和 app 名（除当前 app 外），控制体积。

### 6.4 隐私 —— 必须在产品层面处理

开启修正意味着**你说的每句话都会发到第三方服务器**，而且带着最近的上下文。这是当前版本没有的性质变化，必须显式处理：

1. **首次开启时强提示**：明确告知文本将发送到所选服务商，并说明上下文机制
2. **上下文开关独立**：允许「开修正但不发上下文」（只修正当前这一句）
3. **敏感 app 黑名单**：在黑名单 app 中一律走快速模式，绝不发送。默认预置：1Password、钥匙串访问、系统设置、各类银行/支付网页
4. `docs/PRIVACY.md` 同步更新

第 3 条是我主动补的——用户在密码框里用语音输入的概率不高，但一旦发生，后果是把密码发给第三方 LLM。这个失败模式的代价远大于实现成本。

## 7. 纠错沉淀闭环（第 2 层 → 第 1 层）

这是整个方案里最有长期价值的部分，直接回应"规则覆盖不全，犯的错也时常有变化"。

### 7.1 机制

1. 每次修正产生一组 diff（`克劳德 → Claude`、`那个 → ∅`…），记录到本地纠错日志
2. 当**同一个 diff 在不同上下文里重复出现 ≥ 3 次**，判定为稳定模式
3. **过歧义关**（见 §7.2）——只有无歧义的才进入建议列表
4. 菜单栏出现一个不打扰的角标 → 点开是建议列表
5. 用户一键采纳 → 写入专名词典（或替换规则）→ 以后零延迟、零成本修好
6. 已采纳的词进入上下文（§6.1）与火山热词表，形成正反馈

### 7.2 歧义关：什么能下沉，什么永远不能

这是整个闭环最容易做错的地方。**不是所有重复出现的修正都能变成规则。**

| 类型 | 例子 | 判据 | 处理 |
|---|---|---|---|
| **无歧义** | 克劳德 → Claude | 源词本身不是合法输入，没人真想打"克劳德" | ✅ 可下沉成规则 |
| **有歧义** | cloud ↔ claude | 源词本身也是合法词，用户日常两个都说 | ❌ **永远不下沉**，留在模型层 |
| **纯语境** | 同一个音在不同话题写不同词 | 正确写法取决于上下文 | ❌ 只能靠模型 |
| **词形变体** | 克劳德/Cloud/cloud code → Claude Code | 部分安全部分危险 | ⚠️ 逐条判 |

**怎么判**：修正时让模型顺带标注每处改动 `safe_as_rule: true/false` ——"这个替换在任何语境下都成立吗？"。只有 `true` 的才计入统计并进入建议列表。这比在本地写启发式规则准得多，而且是零额外成本（同一次调用里返回）。

采纳时的兜底：建议列表里每条都显示"最近 3 次的原句"，用户能自己看出这个替换是否会误伤。

### 7.3 为什么这个闭环是必要的

没有它，方案就是"每次花 2 秒和一次 API 调用修同一个词"——功能可用但不进化。有了它：

- **无歧义高频错下沉到零延迟层**，快速模式也能修好
- **有歧义和长尾留给模型**，那是它真正不可替代的部分
- 用户不用手工想"我该加什么词"，系统从真实数据里发现

### 7.4 快速模式的后台学习（可选，默认关）

进阶选项：快速模式粘贴后，后台仍静默跑一次修正，**结果不改已粘贴文本**，只写入历史和纠错日志。好处是即使日常用快速模式，系统仍在学习你的常错词。代价是产生用户没预期的流量，所以默认关，放在高级设置里，开启时说明"会在后台产生额外 API 调用"。

## 8. 浮动面板的状态设计

| 状态 | 面板表现 |
|---|---|
| 录音中 | 同现在，实时上屏 |
| 修正中（精修） | 显示规则处理后的文本 + 顶部细进度条 +「Esc 直接粘贴原文」提示 |
| 修正完成（精修） | 显示修正版，变动处高亮；底部「退回修正前」按钮切换回原文 |
| 已粘贴（快速） | 面板停留至失焦或 Esc；底部「修正」按钮（`⌘Return`） |
| 补修正完成（快速） | 显示修正版 + 变动高亮 +「已复制修正版，⌘V 粘贴」；**不动已粘贴内容** |
| 修正失败/超时 | 显示原文 + 角标「修正未完成，已用原文」 |
| 无 key / 未配置 | 精修快捷键触发时提示一次「未配置修正服务」+ 打开设置的入口，之后按快速模式走 |

两条原则：
- **任何异常都不阻断粘贴**。修正是增强，不是依赖。
- **面板绝不改写已经贴出去的内容**。补修正的产出只进面板和剪贴板，往哪贴由用户决定。

## 11. 建议的实施顺序

分三步，每步独立可用、可验证价值：

**第一步：能用**
- GLM 引擎 + 精修/快速双快捷键 + 先修正后粘贴 + 超时降级
- 纠错 + 语义换行（全在 prompt 里，无设置项）
- 上下文只传「最近 5 条」
- 面板修正中/完成状态

验证的问题：修正质量到底有没有明显提升？1~3 秒延迟在真实使用里能不能忍？

**第二步：好用**
- 专名词典（取代替换规则成为主入口）+ 送入上下文 + 同步火山热词表
- 上下文加入当前 app 名
- 面板 diff 高亮 +「退回修正前」按钮
- 快速模式面板「修正」按钮（`⌘Return`），结果只进剪贴板
- 口语赘词开关（两套 prompt）
- 敏感应用黑名单 + 长度护栏

**第三步：会进化**
- 纠错沉淀闭环（diff 统计 + `safe_as_rule` 歧义判定 + 建议加词）
- Claude API 引擎
- 无头 Claude 订阅引擎（含知情告知）
- 快速模式后台学习

**第一步就应该停下来实测**。如果 GLM 修正在真实语料上带来的提升不明显，或者延迟体感不可接受，后面两步的投入方向都要重新考虑。

## 12. 待确认的开放问题

1. **默认档到底该是精修还是快速？** 方案按用户指定，把单键给了精修。但如果实测发现 2 秒延迟难忍，可能要反过来——单键给快速，组合键给精修。第一步实测后再定。
2. **短文本要不要跳过修正？** 比如 < 10 字的输入（"打开设置"），修正价值低但延迟一样付。倾向：加一个阈值，短文本自动走快速通道。需要实测确定阈值。
3. **热词表内容能否读写？** §6.1.2 的「一份词典两处用」依赖火山 API 支持按 ID 读取、最好还能写入热词表内容。目前 app 只存 ID。若接口不支持，退化方案是本地维护词典、热词表仍靠用户在火山控制台手工同步。需要查火山接口。
4. **现有 `replace-rules.json` 怎么迁移？** 改成「专名词典 + 高级强制替换」后，旧规则需要一次性迁移：右侧目标词进词典，映射关系保留在强制替换里（保持行为不变），并提示用户"其中 N 条可能存在歧义风险"。
